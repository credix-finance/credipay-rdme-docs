--- title: Home fullscreen: false hidden: false --- # Proposta de Reestruturação — Documentação CrediPay > Versão 1.0 — Maio 2026 > Baseado em: mapeamento completo dos Guides + análise comparativa com Claude Platform Docs --- ## 1. Diagnóstico da documentação atual ### O que existe hoje A documentação atual é organizada por **tipo de integração**, não por perfil de usuário. O resultado é uma landing page passiva com listas de links agrupadas em categorias genéricas: Getting Started, Portal do Vendedor, Integração Completa, Integração Parcial. ### Principais problemas - **Entrada genérica:** todos os usuários chegam na mesma porta, sem orientação sobre qual caminho seguir - **Sem jornada:** não há progressão clara de "primeiro passo → próximo passo → produção" - **Perfis misturados:** o vendedor que usa o portal e o desenvolvedor que integra a API acessam o mesmo conteúdo, organizado da mesma forma - **Busca estática:** a documentação não responde perguntas — apenas aponta links - **Sem Ask AI:** usuário precisa saber *onde* buscar, não *o que* perguntar - **VTEX sem página:** a integração VTEX aparece como opção mas retorna 404 ### Oportunidade A CrediPay tem um produto com três caminhos de integração bem definidos e perfis de usuário distintos. Com uma reestruturação orientada a perfis + uma homepage que direciona ativamente, é possível reduzir drasticamente o atrito de onboarding e aumentar a taxa de ativação de novos integradores. --- ## 2. Perfis de usuário ### 2.1 Vendedor Não-técnico **Quem é:** responsável comercial, representante de vendas, gerente de operações que usa a CrediPay exclusivamente via portal web. **O que precisa:** entender o produto, cadastrar compradores, criar pedidos, enviar notas fiscais, consultar status e solicitar reembolsos — tudo sem código. **Dor principal:** se perde em documentação técnica que não é para ele. Quer instruções diretas do tipo "clique aqui, faça isso". **Jornada ideal:** Entender o produto → Criar conta → Adicionar compradores → Criar pedido → Enviar NF → Acompanhar pagamentos → Solicitar reembolso --- ### 2.2 Usuário da Plataforma No-code (operacional) **Quem é:** operador financeiro ou administrativo que gerencia o dia a dia — usuários, limites, reconciliação, desembolsos. **O que precisa:** gerenciar usuários da plataforma, solicitar aumentos de limite, reconciliar desembolsos com o ERP, entender os status dos pedidos. **Dor principal:** precisa de referências rápidas para tarefas operacionais específicas, não de um guia completo do zero. **Jornada ideal:** Gerenciar usuários → Solicitar/acompanhar limites → Reconciliar desembolsos → Consultar status --- ### 2.3 Desenvolvedor / Integrador API **Quem é:** desenvolvedor backend ou fullstack responsável por integrar a CrediPay ao ERP, e-commerce ou sistema de televendas da empresa. **O que precisa:** autenticação, endpoints, fluxos técnicos (e-commerce vs. televendas), webhooks, tratamento de erros e guia de go-live. **Dor principal:** precisa entender o fluxo completo antes de começar a codar. Hoje a documentação técnica está fragmentada em muitas páginas sem uma visão sequencial clara. **Jornada ideal:** Entender o ciclo → Autenticar → Criar compradores → Criar pedidos → Formalizar com NF → Configurar webhooks → Testar → Go-live --- ### 2.4 Integrador VTEX **Quem é:** desenvolvedor ou parceiro técnico que usa VTEX como plataforma de e-commerce e quer adicionar CrediPay como método de pagamento. **O que precisa:** guia específico de instalação do conector VTEX, configuração, mapeamento de campos e resolução de problemas comuns. **Dor principal:** precisa de um guia 100% focado em VTEX — não quer ler documentação genérica de API. **Jornada ideal:** Pré-requisitos → Instalar conector → Configurar → Testar → Go-live → Troubleshooting --- ### 2.5 Gestor / Financeiro **Quem é:** CFO, controller, analista financeiro que precisa entender o produto para tomada de decisão ou acompanhar a operação financeira. **O que precisa:** entender como funciona o crédito, os prazos, os desembolsos, como reconciliar com o ERP e como interpretar os relatórios. **Dor principal:** não precisa saber como integrar, mas precisa entender o produto com profundidade financeira. **Jornada ideal:** Entender o produto → Glossário de termos → Como funciona o crédito → Desembolsos e reconciliação → Tipos de transação --- ## 3. Funcionalidade Ask AI ### Conceito Um campo de busca semântica na homepage (e em todas as páginas) que responde perguntas em linguagem natural sobre a documentação, sem exigir que o usuário saiba qual página consultar. ### Como implementar A documentação já tem um `llms.txt` disponível em `https://docs.credipay.credix.finance/llms.txt` — o mesmo mecanismo que a CrediPay usa para integrar com IDEs como Cursor. O Ask AI pode ser construído sobre esse arquivo usando qualquer LLM com RAG. ### Exemplos de perguntas que o Ask AI resolveria - *"O que acontece se o comprador não aprovar o pedido em televendas?"* - *"Qual a diferença entre DDE e DDF no prazo de pagamento?"* - *"Como eu configuro webhooks no ambiente de staging?"* - *"Quais campos são obrigatórios no POST /v2/orders?"* - *"O XML foi rejeitado com ValidationFailed — o que eu faço?"* --- ## 7. Considerações técnicas ### Plataforma atual A documentação usa **ReadMe.com** (readme.io). A reestruturação pode ser feita inteiramente dentro da plataforma, sem migração. ### O que o ReadMe suporta - Múltiplas seções com URLs customizadas ✅ - Landing page customizável ✅ - Ask AI nativo (feature paga do ReadMe) ✅ - Versionamento (já usado: v1.0 e v2.0) ✅ - API Reference integrada ✅ ### Priorização sugerida 1. **Homepage nova** — maior impacto, menor esforço 2. **Reorganização de URLs** — sem criar conteúdo novo 3. **Seção VTEX** — conteúdo a criar 4. **Páginas de go-live** — conteúdo a criar 5. **Ask AI** — feature nova, depende de plano ReadMe ou implementação custom --- ## 8.
